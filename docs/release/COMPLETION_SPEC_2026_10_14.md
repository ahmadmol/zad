## حالة المشروع المعتمدة عند تسليم هذا الأمر — 14 أكتوبر 2026

المرحلة السابقة أُغلقت وفق تقرير `docs/DARK_MODE_FINAL_QA_2026_10_14.md`، وتقرير تحديث المراجع `REFERENCE_REFRESH_2026_10_13.md`. لا تبدأ بإعادة تنفيذ الـUI من الصفر ولا تكرر مهمة الدارك. ابدأ بقراءة هذه التقارير والأدلة الحالية والتحقق من حالة المشروع الفعلية، ثم نفّذ خطة الإكمال التالية.

**Baseline معلَن من تقرير Codex السابق (تحقق منه قبل العمل):**

- Build ناجح، 452 Unit Tests ناجحة، 12 Android regression tests ناجحة، Lint بلا أخطاء مع **149 warning** بنفس خط البداية.
- 59 وجهة فُحصت في Light/Dark، ولقطات فعلية من المحاكي. هذا **دليل على عرض الواجهات، وليس إثباتًا لاكتمال كل ميزة وظيفيًا**.

- التحقق من دقة بوصلة القبلة ومعايرتها على جهاز حقيقي **لم يكتمل**.
- لم تنفذ المرحلة السابقة Commit أو Push أو Git Reset. حافظ على التعديلات المحلية.

**بوابة التنفيذ الآن:** لا تغيّر ألوان الـDesign System أو أبعاد الـLight/Dark المعتمدة إلا لتصحيح Bug محدد موثق. ابدأ بإحصاء النواقص الوظيفية ومصادر المحتوى ثم نفّذ المتطلبات الأساسية في مراحل، مع Build/Tests ولقطات وتقارير حقيقية بعد كل مرحلة. راجع أي ملف يعدله Agent آخر قبل الكتابة عليه، ولا تسمح بتعديل متزامن على نفس الملفات. إذا عُدِّلت واجهة أثناء إضافة وظائف، يجب أن تظل ملتزمة بمرجعها المعتمد وبنفس تصميم Light/Dark.

**قواعد تسليم مهمة:**

- عند غياب فيديو/بث/ملف صوت/ترخيص أو API مفتاحه غير متاح، لا تصف الميزة بأنها جاهزة ولا تعرض زرًا يعمل شكليًا. وثّق الفجوة وقم بما هو ممكن قانونيًا وتقنيًا دون تزوير نجاح.
- لا تستبدل بيانات القرآن والحديث والدعاء بمحتوى مولّد، ولا تغيّر أي نص قرآني موجود دون الرجوع لمصدر موثوق.
- بيانات Demo لمجتمع إحسان يمكن توليدها محليًا، مع علامة واضحة وفصل عن بيانات المستخدم، ودون أرقام اتصال لأشخاص حقيقيين.
- أي نشاط يتطلب جهازًا حقيقيًا (حساس القبلة، توقيت الإشعارات، تشغيل وسائط معينة) يجب أن يكون له خانة `PHYSICAL DEVICE PENDING` إلى أن يتم اختباره، لا `PASS` بالتخمين.
- حافظ على تفاصيل مخرجات كل مرحلة في `docs/release`، وأصدر قرارًا صريحًا `READY FOR CLOSED BETA` أو `BLOCKED` مدعومًا بالدليل.

## أمر التنفيذ الشامل

## 0. النتيجة المطلوبة، وليس مجرد شكل الشاشة

أريد إكمال تطبيق **إحسان** بالكامل إلى **نسخة Release Candidate جاهزة لتجريب شامل مع مستخدمين فعليين (closed beta)**، مع UI/UX نظيف احترافي ومتناسق، ومحتوى ديني موثق، ووظائف تعمل حقيقةً ضمن حدود نسخة Android المحلية الحالية. واجهات التطبيق يجب أن تكون غنية بالمحتوى **عندما تتوافر بيانات حقيقية أو تجريبية مصرح بها**؛ وفي حالات عدم الاتصال أو نقص المصدر يجب أن تعرض حالة صحيحة لا فراغًا أو نجاحًا وهميًا.

الهدف هو تجربة مكتملة مشابهة **من حيث مستوى الجودة وثراء الميزات وسلاسة الاستخدام** لتطبيقات إسلامية ناضجة، وليست نسخ هويتها أو أصولها أو محتواها المحمي. اجمع هوية «إحسان» الإسلامية (القرآن والصلاة والقبلة والذكر والحديث والمحتوى التعليمي) مع قسم المجتمع والتبرع المحلي.

**تمييز إلزامي:** لا يمكن الادعاء أن التبرعات والحسابات والطلبات متعددة المستخدمين «جاهزة للإنتاج الفعلي» دون Backend آمن ومصادقة ومراجعة محتوى وآليات حماية. أريد الآن نسخة **Feature-Complete Beta** تعمل محليًا ببيانات تجريبية موسومة بوضوح، مع إعداد بنية تسهل ربط Firebase أو Laravel لاحقًا. لا تُنفذ Backend الآن ولا تصطنع اتصالات أو عمليات دفع أو تنسيق حقيقية.

## 1. قواعد مانعة للأخطاء السابقة

1. **اقرأ المشروع بالكامل قبل التعديل:** الشاشات، Routes، ViewModels، Repositories، Room، DataStore، الـdesign system، الاختبارات، ومخرجات الخطة المنفذة سابقًا.
2. احتفظ بكل الشغل المحلي السابق. لا `git reset`/`checkout` المدمّر ولا commit/push، ولا تفترض أن فرعًا آخر أو محادثة أخرى أنهت التعديلات. عند تعديل متزامن: أوقف ذلك الملف واطلب تنسيق الملكية قبل المتابعة.
3. **الصور المرجعية هي مرجع بصري** للـlayout والـdensity والـtypography. لا تعِد تصميمها عشوائيًا، ولا تكبّر النصوص والمسافات جماعيًا. الصور ليست مصدرًا موثوقًا لصحة نصوص القرآن أو الحديث أو مواقيت الصلاة أو حالة بث مباشر.
4. **ممنوع عناصر شكلية غير عاملة:** الأزرار والتبويبات والمفضلة والبحث والفلترة والتذكيرات والتنزيلات والحفظ والمشاركة والتواصل والصوت يجب أن تفعل شيئًا حقيقيًا مطابقًا لتسميتها. إن تعذّر دعم ميزة بصدق، اعرض «غير متاحة في النسخة التجريبية» بشكل واضح وسجّل blocker؛ لا تجعل زرًا نشطًا مزيفًا.
5. **لا بيانات دينية مختلقة** ولا آيات/أحاديث/أدعية/درجات صحة/أسانيد/أوقات صلاة أو ملخصات تنسب للقرآن والسنة دون تحقق. لا تولّد محتوى دينيًا بثقة زائفة.
6. لا تُدخل عمليات شبكة أو APIs داخل Composables. حافظ على Architecture الحالية، ViewModels، فصل Data/Domain/Presentation، وتجنب dependencies غير الضرورية.
7. لا تخلط الداتا التجريبية بالمعلومات الحقيقية أو بيانات أشخاص حقيقيين. لا تستخدم أرقام هواتف أو معلومات شخصية لأشخاص حقيقيين في seed.
8. لا تغيّر ألوان Light Mode أو شكل الصفحات الجيد بلا داعٍ. لا تغيّر geometry بين Light/Dark. احترام RTL وSafeArea وfont scale إلزامي.

- `docs/release/DEMO_DATA_MANIFEST.md`: مكونات الداتا التجريبية والعدد ومصدرها وطريقة reset وإشارة Demo.

## 3. اكتمال القرآن — P0

- اعتماد قارئ **مصحف صفحة بصفحة** يضم **السور الـ114** وتخطيط صفحات **604 صفحة للنسخة/الرسم المعتمد**، مع ربط ثابت موثق بين رقم الصفحة والسورة/الآية/الجزء. لا تستخدم 604 صورة مصممة بالذكاء الاصطناعي ولا تكرر صفحة الفاتحة. استخدم النص المضبوط والترقيم/حدود الصفحات من مصدر موثوق ومتوافق مع ترخيصه.
- استخدم `quran_page_background` المرفق كإطار زخرفي إن كان مناسبًا، وأعرض النص الحقيقي فوقه. العنوان/عدد الآيات/علامات الوقف/رقم الصفحة يجب أن يكونوا مطابقين للمصدر، لا لما يظهر في mockup. **أولوية دقة رسم الآيات وترقيمها على مطابقة الصورة**.
- تجربة صفحة كاملة، Swipe صفحات باتجاه صحيح RTL، Jump إلى سورة/جزء/صفحة/آية، قائمة السور والأجزاء، حفظ آخر صفحة وموقع قراءة بعد إغلاق التطبيق، Bookmarks محفوظة، الانتقال إلى العلامة، تحديد آية عند الإمكان، نسخ/مشاركة مع المرجع، بحث نصي صحيح، واستعادة حالة القراءة.
- قارئ صوت عملي يتيح **أكثر من قارئ متحقق من توفر ملفاته وحقوق استعمالها**، اختيار القارئ، تشغيل/إيقاف، السابق/التالي، الاستمرار عبر انتقال الصفحات عند توفر الربط، تقدم حقيقي، وحالات buffering/error. لا تعرض اسم قارئ أو أيقونة تنزيل/تكرار إلا إذا تعمل فعلًا. إذا كانت الحقوق تسمح، ادعم تنزيلًا وتخزينًا محليًا وتقدم التنزيل والحذف؛ وإلا وضح عدم توفر التنزيل.
- خيارات قراءة حقيقية: حجم الخط بما لا يفسد تصميم الصفحة أو ضبط layout، سطوع/نمط القراءة إن كانت مدعومة، إخفاء/طي المشغل، الاستئناف. لا تدع المشغل يغطي آخر سطر من المصحف.
- **استثناء الثيم:** ورقة المصحف نفسها تظل عاجية دافئة `#F8F3E7` بخط `#123A32` وزخرفة خضراء/ذهبية، ولو التطبيق Dark؛ يبقى الـapp chrome والمشغل Dark.
- اختبارات البيانات: كل صفحة مملوءة بالنص الصحيح، لا آية مكررة بسبب الربط، الآية في سورتها الصحيحة، تزامن الصفحات والعلامات بعد إعادة فتح التطبيق، تحقق من سور طويلة وقصيرة والحدود بين الأجزاء.

## 4. الصلاة والقبلة والتاريخ والإشعارات — P0

- مواقيت الصلاة الخمس + الشروق على أساس **إحداثيات حقيقية أو مدينة يختارها المستخدم**، يوم وتوقيت محلي صحيح، DST، الحساب المعتمد، خيار المذهب للعصر عند الحاجة، وطريقة الحساب ضمن الإعدادات، دون قيم ثابتة داخل UI. قارن عينات بمصدر مواقيت معروف، مع بيان أن الطرق الحسابية قد تختلف عن التقاويم المحلية.
- الـHero يعدل الصلاة التالية والعدّ التنازلي آنيًا وينتقل تلقائيًا بعد الوقت؛ عرض الجدول والـcalendar الحقيقي؛ دعم عدم سماح الموقع مع اختيار مدينة يدويًا.
- القبلة: زاوية من الموقع للكعبة محسوبة، دوران البوصلة بواسطة Sensors مع معالجة lifecycle والمعايرة والتشويش وغياب المستشعر. لا تجعل «الدقة جيدة» تظهر ثابتة ولا تعرض درجة ثابتة مثل `206°` لكل المستخدمين. عند عدم دعم sensor اعرض الاتجاه كزاوية محسوبة مع حالة واضحة.
- إشعارات الصلاة/الأذكار/التذكيرات تعمل حسب أذونات Android ونظام التنبيهات وقيود البطارية. اختبر تغيّر المنطقة الزمنية، تغيير الساعة، إعادة تشغيل الجهاز، إلغاء/تعديل التذكير وعدم تكرار إشعارات زائفة.
- التقويم الهجري مصدره طريقة محددة مع إمكانية offset عند الحاجة؛ لا تخلط التاريخ التجريبي في صور التصميم بالتاريخ الحي.

## 5. الأحاديث الصحيحة — P0

- واجهة أحاديث مكتملة: تصنيفات/كتب/قوائم/تفاصيل/بحث/فلترة/مفضلة/مشاركة/استمرار. **الداتا كثيرة ومتنوعة، لكن الجودة أولًا**؛ استورد مجموعة كبيرة من مصادر موثوقة بعد التحقق من الحقوق والترخيص.
- لكل حديث: نص عربي كامل موثوق، اسم الكتاب، الباب أو التصنيف، رقم الحديث/المرجع (وعند اختلاف الترقيم وضّحه)، الحكم/درجة الصحة **فقط إذا موجودة وموثقة في المصدر**، وبيانات المصدر/الإصدار. لا تضع «صحيح» لجميع الأحاديث آليًا، ولا تنسخ الأحكام من AI.
- مبدأ الإطلاق: لا تعرض شيئًا باسم حديث نبوي إن لم يمر التحقق، ولا تضف أحاديث مولّدة لمجرد تكثير العدد. تحقق من Unicode، التشكيل، أسطر النص، التشابه والتكرار.

## 6. الأدعية والأذكار وأسماء الله الحسنى والتسبيح — P0

- الأدعية: اجعل كل الأقسام المرجعية مملوءة **بنصوص موثقة متاحة فعليًا**، مع المصدر والنوع، البحث/التصفية، تفاصيل الدعاء، مشاركة/نسخ/حفظ؛ ميّز الأدعية القرآنية والنبوية والمأثورة عن النصوص العامة. لا تنسب كلامًا غير موثق إلى القرآن أو النبي.
- الأذكار: أذكار الصباح والمساء وبعد الصلاة والنوم وغيرها وفق مصادر ومراجع موثوقة، مع العدد المستهدف لكل ذكر إن كان موثقًا، عدّاد تفاعلي، تقدم محفوظ، العودة لليوم التالي وسياسة reset صحيحة.
- أسماء الله الحسنى: اكتمال مجموعة الأسماء وفق القائمة/المصدر المعتمد في المشروع، المعاني من مرجع موثوق مع نسبة المصدر. صفحات تفاصيل وتأملات لا توهم أنها نصوص دينية منقولة إذا كانت شروحًا تحريرية.
- التسبيح: ذكر مختار/عدد/هدف/إعادة ضبط/إحصاءات فعلية حسب يوم/أسبوع/شهر؛ تخزين فعلي وليس أرقامًا مصطنعة أو Chart مصمتًا، بما في ذلك الحالات الصفريّة.
- النشاطات والإحصائيات: بيانات مشتقة من أفعال المستخدم الحقيقية أو Demo scenario معلوم، ولا تعرض تقدمًا شخصيًا موهومًا بعد التثبيت الحقيقي.

## 7. البث المباشر والفيديو والتعلّم — P0

- افحص قسم الحرم المكي والمسجد النبوي والبثوص الأخرى. اختر **مصادر بث رسمية مرخّصًا بتضمينها** وأثبت التشغيل الحقيقي على جهاز Android، توافر الإنترنت، وصحة الفيديو الجاري والـthumbnail؛ لا تعتبر صورة + زر تشغيل «بثًا مباشرًا».
- لا تضع `مباشر` على فيديو مسجّل أو رابط متوقف. عند توقف المصدر اعرض «البث غير متاح مؤقتًا» مع إعادة محاولة/مصدر رسمي بديل؛ لا تخترع streaming URLs أو تكسر سياسة YouTube لاستخراج فيديوهات مباشرة.
- `سنحيا بالقرآن` و`نبي الإحسان`: استكمال قوائم الحلقات والتفاصيل ومصادرها/آياتها/الدروس/المفضلة/لاحقًا/البحث/الفلاتر والروابط بين السلسلة والحلقات؛ المحتوى التحريري الملخص يذكر المصدر، ويُراجع دينيًا قبل نسبه لمصدر. لا تلفّق وصفات نبوية أو أسماء حلقات أو روابط.
- لكل Video: عنوان حقيقي، رابط قابل للفتح حاليًا، مصدر/ناشر واضح، thumbnail صحيحة، المدة إن أمكن التحقق، نوع المحتوى، تصنيف، ملخص **مراجع**، حالة تشغيل وفشل. لا تكرر رابطًا واحدًا في 20 بطاقة.
- استخدم الـplayer المتوافق مع المصدر وشروطه. لا تستبدل مشغل YouTube بتحميل أو تشغيل مباشر غير مصرّح به. أي تنبيه «ليس بثًا» أو «محتوى خارجي» يكون صريحًا.

## 8. مجتمع إحسان: العروض والطلبات والحساب — P0 في Demo Mode

- أغنِ المجتمع ببيانات **تجريبية محلية واقعية ومتنوعة وموسومة DEMO**: عروض/طلبات (تعليم، أغذية، أثاث، ملابس، علاج، سكن...) بصور مرخّصة أو assets أصلية، حالات متنوعة، مدن، تواريخ متسقة، وصف مفصل، صور متعددة إن تم دعمها؛ لا تعرض أشخاصًا حقيقيين أو أرقام تواصل حقيقية.
- شاشات المجتمع كلها مكتملة: التبويبات، البحث والفلترة وترتيب النتائج، القوائم، التفاصيل، معرض الصور، إنشاء عرض وطلب بثلاث خطوات، حفظ مسودة، تعديل وحذف ضمن ملكية محلية قابلة للتعقب، سجل المساهمات، إدارة العروض والطلبات، المشاركة، والمفضلة إن كانت ضمن المشروع.
- اختبر سيناريو كاملًا: إنشاء عرض Demo ← حفظ الصور/البيانات ← ظهوره في القائمة والتصفية ← فتح التفاصيل ← إدارة الحالة المحلية ← الظهور في السجل، وكذلك سيناريو طلب المساعدة.
- **لا تدّعِ أن التبرع نُفِّذ أو تم التحقق من حالة، أو حدثت عملية مالية، أو تواصل طرفان** دون Backend حقيقي. لا يوجد دفع داخل التطبيق الآن. شاشة «لوحة إحسان المحلية» تبين بوضوح أن الحالات محلية على الجهاز وغير متحقق منها رسميًا.
- بيانات الملكية لا تُستنتج من الاسم وحده؛ استخدم ID محليًا ثابتًا لمالك السجل التجريبي. لا تسمح بحذف سجلات حساب آخر اصطناعيًا.
- أعط المستخدم خيار `Demo reset` لا يمس القرآن/الأذكار/الإعدادات الشخصية دون تأكيد ومحددات واضحة.

## 9. البحث والملف الشخصي وباقي الشاشات — P0

- بحث شامل فعّال ضمن محتويات مدعومة فعليًا: القرآن، الأحاديث، الأدعية، الأذكار، أسماء الله، الفيديوهات، المجتمع، مع نتائج مصنفة وإحالة إلى التفاصيل الصحيحة؛ لا تعرض فئة في فلاتر البحث ما لم يكن البحث يدعمها. عالج Arabic normalization بعناية بحيث لا يغير النص القرآني المخزن.
- الملف الشخصي: حفظ الاسم، المدينة، الصورة والنبذة، الإلغاء والتراجع، سجل المستخدم، البيانات المحلية، الخصوصية، الإعدادات والتصدير/الحذف فقط إذا نفذت فعلًا. لا تعرض معلومات شخصية أو حسابًا سحابيًا وهميًا.
- جميع عناصر الشاشة الرئيسية والخدمات والبحث والإعدادات والإحصائيات والتذكيرات والبث والمفضلة/لاحقًا والتنزيلات والـOnboarding: الوصول إليها عبر Routes، وسلوك الضغط، Back، restoring state، حالات Empty/Error/Offline. لا تبقِ صفحة موجودة وغير قابلة للوصول.
- الصور داخل Cards لا تُقص بشكل يخفي الموضوع؛ لا blank gray strips، ولا overflows، ولا placeholder دائم عند وجود بيانات.

## 10. البيانات التجريبية والمحتوى: سياسة صريحة

### 10.1 بيانات Demo مصطنعة **مسموحة**
أسماء عروض محلية خيالية، صور توضيحية مسموحة، مدن، حالات تبرع/طلبات موسومة Demo، إحصاءات حساب تجريبي، تذكيرات تجريبية قابلة للتعديل. استخدم بيانات حتمية (deterministic seed) ولها IDs ثابتة؛ لا تنشئ duplicate seed عند كل تشغيل. أضف اختبار reset/reseed وعزل بيانات demo عن بيانات المستخدم.

### 10.2 محتوى يجب أن يكون **موثوقًا** وليس Demo مولّدًا
القرآن، التجويد/الآيات، الأحاديث ودرجاتها، نصوص الأدعية المأثورة والأذكار وأعدادها، نسب الأحكام والمراجع، مواقيت الصلاة والقبلة. هذه تُستمد من مصدر قابل للتحقق وتخضع لتدقيق وربط metadata؛ إذا تعذر المصدر لا تختلق محتوى، بل سجّل blocker واضح.

### 10.3 فيديوهات وروابط فعلية
لا تستخدم روابط YouTube متخيلة أو قصيرة غير مختبرة. اعمل manifest لكل رابط `id/url/title/channel/verified_at/embeddable/licensing/thumbnail/status`. اختبر عدة روابط لكل سلسلة، مع fallback حقيقي إن توفر.

## 11. مصادر مرشّحة يجب فحص الترخيص والوصول أولًا (ليست موافقة تلقائية)

- **نص القرآن:** https://tanzil.net/docs/Text_License — يسمح بنسخ النص دون تعديل مع شروط نسبة المصدر والإشعار الترخيصي. اختبر التوافق مع تطبيقك قبل التضمين.
- **صفحات/آيات/قراء ومعلومات صوت:** https://api-docs.quran.com/ — تدعم Content APIs بيانات الصفحة والآية والتلاوة، **لكن** الوصول قد يتطلب اعتمادًا وسرًا محفوظًا في Backend؛ لا تضع `client_secret` داخل APK. إن كان Backend مؤجلًا، اختر مصدرًا محليًا/عامًا مناسبًا مرخّصًا أو سجّل blocker للصوت المتعدد إلى حين استيفاء شروط الوصول.
- **الحديث:** https://github.com/sunnah-com/api و https://beta.sunnah.com/developers — مصدر محتمل؛ الوصول للـAPI يحتاج مفتاحًا، ويجب مراجعة شروط الاستخدام والتغطية والحقوق قبل الاستيراد.
- **مواقيت الصلاة والقبلة:** https://github.com/batoulapps/adhan-kotlin — مرشّح لحسابات الصلاة/اتجاه القبلة، بعد التأكد من توافق نسخته مع Kotlin/Android وطرق الحساب المطلوبة.
- **YouTube:** https://developers.google.com/youtube/terms/required-minimum-functionality — اتبع سياسات التشغيل/التضمين، ولا تحجب الـbranding والcontrols ولا تتحايل على روابط البث.

لا تضف اعتمادًا على API يحتاج مفتاحًا أو Backend دون تنبيه واضح. لا تفترض أن أي مكتبة/ملف قرآن متاح تجاريًا بلا شروط. حفظ الحقوق ونسب المصادر ضمن About/Attributions إلزامي.

## 13. الجودة التقنية والاستقرار والأمان

- تقليل crash/ANR، تحسين startup والـscroll والصور/الذاكرة، lifecycle للـplayer/sensors/location، استعادة الحالة عند rotate/process recreation، وعدم إبقاء الصوت أو المستشعر يعمل بلا سبب.
- اختبار Offline/slow network/no permission/no sensor/empty search/long Arabic text/font scale 1.3 وتغير المدينة والتوقيت ودخول/خروج التطبيق.
- لا تجمع بيانات حساسة دون ضرورة. بيانات Demo مفصولة، الحذف المحلي حقيقي مع confirmation، لا روابط خاصة أو token في repo/APK، ولا تطلب permissions غير لازمة.
- عالج Room migrations بعزل واختبار. **لا تمسح قاعدة البيانات أو تستخدم destructive migration**. اختبر الترقية من مخططات مستخدمة فعلًا بما فيها `prayer_log` والصور القديمة، إن طُلبت migration.
- `ProGuard/R8` وRelease configuration وAndroid manifest permissions ونسخ resources وإزالة Debug logs الحساسة تُراجع بحسب إعدادات المشروع، دون تحديث Gradle/Kotlin/AGP عشوائي.

## 14. جدول التنفيذ الإلزامي (بدون تعديلات عشوائية)

**Gate 0 — Audit + Baseline:** قائمة شاشات كاملة، اختبارات وبناء baseline، سجل مشاكل وأصول ومصادر، فهم التغييرات السابقة. لا تبدأ إعادة رسم 30 شاشة دفعة واحدة.

**Gate 1 — Core Religious Features:** القرآن 114/604 والقراءة والحفظ والصوت المدعوم؛ الصلاة والقبلة والتذكيرات؛ الحديث والأذكار والأدعية. أي نقص ديني موثق يظل blocker وليس نصًا مختلقًا.

**Gate 2 — Media & Learning:** البث الحقيقي أو تصريح انقطاع المصدر، تشغيل الفيديو، سنحيا بالقرآن ونبي الإحسان والوصفات المرتبطة ومفضلة/لاحقًا والملخصات المراجعة.

**Gate 3 — Ihsan & Account:** تعبئة Demo محلي موثوق، كامل CRUD والتفاصيل وخطوات الإدخال والصور والإدارة والسجل والملف والبحث.

**Gate 4 — Visual/Functional Closure:** شاشةً شاشةً وفي الثيمين، مراجعة الملاحظات وإغلاق P0/P1، اختبارات صارمة، APK جاهز للتجربة + تقرير تسليم.

بعد كل Gate قدم تقريرًا بالأشياء **المنفذة فعلًا** مع اختبارات/صور، ولا تكرر جملة «مكتمل» لميزة لا تملك دليل نجاح لها. إذا واجهتك مشكلة تمنع اكتمال ميزة أساسية (حقوق البيانات/مفتاح API/مصدر بث/مراجعة دينية)، دوّنها وحدد المطلوب منّي دون إدعاء تجاوزها.

## 15. معايير قبول لا تقبل المجاملة

1. **Route inventory = 100%:** لكل Route حالة اختبار أو توثيق لإزالتها إن كانت مهجورة، ولا شاشة متاحة للمستخدم بلا عنوان ومحتوى مناسب أو Empty state صحيح.
2. **Button/function audit = 100% للأزرار الظاهرة:** كل CTA/Filter/Switch/Share/Save/Retry/Back يقوم بالسلوك المعلن؛ لا أزرار مزيفة.
3. **Content integrity:** جميع آيات المصحف المكتمل ومراجعها صحيحة، لا أحاديث/أدعية مولّدة، حقوق المصادر محفوظة. أي ربط بيانات مفقود لا يوصف بالمكتمل.
4. **Demo coverage:** كل نوع شاشة مجتمعية له أمثلة متنوعة (active/pending/completed وغير ذلك) ومعلومات متسقة، ويمكن تجربة create/edit/delete/reset/relaunch دون تضارب.
5. **Media functionality:** كل فيديو معلن متاح تم تشغيله واختباره أو تم توصيفه بوضوح غير متاح؛ لا "Live" وهمي.
6. **UI:** Light/Dark جنبًا إلى جنب، 360/393/412/600dp، RTL، fontScale 1.0 و1.3؛ لا clipped chips/images/text أو محتوى تحت bottom bar، ولا giant whitespace أو hard-coded بيانات بصرية غير واقعية.
7. **Functional tests:** سيناريوهات كاملة للقرآن، الصلاة والقبلة، إشعار، حديث، ذكر، بحث، فيديو، إنشاء عرض/طلب، سجل، تعديل ملف شخصي، Offline، حفظ وإعادة فتح.
8. **Build:** Gradle `assembleDebug`، `testDebugUnitTest`، `lintDebug`، واختبارات Android/Compose المتاحة، ثم بناء Release Variant قابل للتثبيت وفق إعدادات التوقيع المتاحة؛ لا تزعم إنتاج Signed Release إن لم تتوفر مفاتيح التوقيع. **لا تستخدم `flutter analyze`.**
9. **No unresolved P0:** أي P0 غير مغلق = `BETA BLOCKED` ويظهر صراحة في التقرير، ولا يحق وصف النسخة بأنها إنتاجية أو نهائية.
